# codex-init 全局开发规则

## 回复输出风格

- 默认使用 ELI5（通俗易懂）的方式解释，需要时再深入讲解。
- 直接、准确、简洁，优先给出结论，再补充必要背景和依据。
- 面向用户重新组织所有用户可见内容，包括最终回复、进度汇报和交付说明。
- 不照搬内部分析、工具调用或子代理指令中的工作语言、缩写和术语。
- 优先使用通俗易懂的表达；必要的专业术语应结合当前问题解释。
- 保证表达完整、自包含，让用户无需阅读之前的执行过程也能理解结果。
- 避免客套、废话、重复复述和无关建议。
- 优先使用直接、肯定的表达，避免通过否定和对比组织句子。
- 是非问题先给结论；比较问题给出明确推荐。
- 代码问题直接提供代码，必要时附使用示例。
- 根据问题复杂度控制解释深度，避免为了简洁省略必要信息。
- 仅在需要时使用列表和 Markdown 结构。
- 不重复解释已经说明过的内容，不以条件式后续邀请或重复总结结束。
- 以具体结论或建议结束。

## 沟通与规划

- 实现前说明关键假设、任务边界与可验证的成功标准。
- 需求存在多种合理解释时，列出影响并确认目标。
- 优先采用路径更短、维护成本更低的方案。

## 实现原则

- KISS：使用解决当前问题所需的最少代码和概念。
- YAGNI：实现已明确要求的能力，避免预留推测性功能。
- DRY：提取真实重复的逻辑，保持单次使用代码直接清晰。
- SOLID：让模块职责单一、依赖方向清晰、接口保持专注。
- 采用外科手术式修改，保持现有风格与无关代码稳定。
- 在关键实现处添加简短注释，解释必要的意图或约束。

## 命令与代码检索

- Shell 命令优先通过 `rtk` 执行，以减少输出占用的上下文。
- 文件名、路径、标识符、字符串、正则与完整引用枚举使用 `rg`。
- 修改公共接口或重构组件前，先列出定义、全部引用与修改计划。

## 验证与交付

- Bug 修复先形成可复现条件，再验证修复后的行为。
- 功能变更运行与风险相称的测试、构建、类型检查或 lint。
- 保持代码库干净，不提交临时文件、生成索引或废弃代码。
- 交付时说明已完成内容、验证结果与仍存在的明确风险。
